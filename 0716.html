CONCEPT

일반 응답 vs 스트리밍 응답

TTFT와 체감 속도, 그리고 스트리밍의 동작 흐름

개념 정리

  • 일반 응답: 클라이언트가 요청을 보내면 서버는 LLM이 답변 전체를 다 만들 때까지 기다렸다가 한 번에 응답
  • TTFT(Time To First Token): 요청 후 첫 글자가 화면에 보이기까지 걸리는 시간. 응답 품질만큼 중요한 UX 지표
  • 스트리밍 응답: LLM이 토큰을 생성하는 즉시 백엔드로 흘려보내고, 백엔드는 버퍼링 없이 그대로 클라이언트로 전달
  • 흐름: 요청 -> chunk 1 -> chunk 2 -> chunk 3 -> ... -> [DONE], 하나의 HTTP 응답 안에서 연결이 끝까지 유지됨
  • 토큰(token): LLM이 텍스트를 처리/생성하는 최소 단위 / chunk: 네트워크로 한 번에 전송되는 데이터 묶음
  • 클라이언트는 chunk를 누적해서 합쳐야 완성된 답변이 됨
같은 5초짜리 답변이라도 방식에 따라 체감이 다르다. 사람은 "기다림"보다 "진행되고 있다는 신호"에 훨씬 민감하다.

FAQ

스트리밍이 왜 체감 속도를 높여줘?

전체 응답 시간은 같아도, 첫 토큰이 빨리 도착해서 "진행 중"이라는 신호를 바로 주기 때문에 대기 시간이 짧게 느껴진다.

chunk와 토큰은 같은 개념이야?

아니다. 토큰은 모델이 텍스트를 다루는 최소 단위이고, chunk는 그 토큰(들)을 네트워크로 실제 전송할 때 묶이는 데이터 단위다.

IMPLEMENTATION

FastAPI 스트리밍 엔드포인트 구현

/chat, /chat/stream, /chat/stream/v2 구현 및 디버깅

개념 정리

  • 일반 엔드포인트(/chat)는 response_model로 pydantic 모델을 지정, 완성된 응답을 한 번에 반환
  • 스트리밍 엔드포인트는 StreamingResponse와 제너레이터 함수(yield)로 chunk를 순차 전송
  • 모델 파라미터는 서비스마다 허용 목록이 다를 수 있음 (예: gpt-4o-mini는 거부, gpt-5-mini만 허용)
  • system 프롬프트를 messages 배열 맨 앞에 추가하면 응답 스타일(길이, 언어 등)을 제어할 수 있음

핵심 코드

ESSENTIAL def chat(req: ChatRequest): completion = call_llm(req.message) answer = completion.choices[0].message.content return ChatResponse(reply=answer, model=completion.model) @app.post("/chat/stream/v2") def chat_stream_v2(req: ChatRequest): def gen(): stream = client.chat.completions.create( model=req.model or MODEL, messages=[ {"role": "system", "content": SYSTEM_PROMPT_V2}, {"role": "user", "content": req.message} ], temperature=req.temperature if req.temperature is not None else 0.7, stream=True, ) for chunk in stream: ... yield piece return StreamingResponse(gen(), media_type="text/plain")

FAQ

ChatResponse(reply=...)인데 왜 pydantic 검증 에러가 났어?

모델 정의(class ChatResponse(BaseModel))에는 필드명이 answer로 되어 있는데 함수에서는 reply로 넣고 있어서 발생했다. 원하는 출력 필드가 reply라면, 함수가 아니라 모델의 필드명을 reply로 바꿔야 한다.

400 BadRequestError는 왜 났어?

사용 중인 API 엔드포인트가 허용하지 않는 모델명(gpt-4o-mini)을 요청했기 때문이다. 에러 메시지에 명시된 허용 모델 목록(gpt-5-mini)으로 맞춰야 한다.

DEBUGGING

스트리밍 chunk 안전 처리

빈 choices, None piece, 예외 처리까지

개념 정리

  • 모든 chunk에 choices가 들어있는 건 아님 — 비어있는 경우 [0] 인덱싱 시 IndexError 발생
  • delta.content가 None이거나 빈 문자열인 chunk는 결과에 포함하면 안 됨
  • 예외 발생 시에도 스트림을 그냥 끊지 않고, 에러 마커를 한 줄 yield해서 클라이언트가 인지하게 함

핵심 코드

ESSENTIAL for chunk in response: if not chunk.choices: continue piece = getattr(chunk.choices[0].delta, "content", None) if not piece: continue collected.append(piece) yield piece # 예외 마커 except Exception as e: yield f"\n[ERROR] {type(e).__name__}: {e}"
if piece: 한 줄이 None과 빈 문자열을 동시에 걸러준다 (둘 다 falsy). f-string(f"...")을 빼먹으면 중괄호 안의 변수가 텍스트 그대로 출력되니 주의.

FAQ

continue 대신 if로 감싸도 결과가 같아?

로직상 결과는 동일하다. if chunk.choices: 로 감싸도, if not chunk.choices: continue 로 걸러도 빈 chunk는 처리에서 제외된다. 다만 후자가 "건너뛰기" 의도를 더 명확히 드러낸다.

CONCEPT

동기 제너레이터 vs 비동기 제너레이터

for/yield와 async for/await/yield의 실행 차이를 코드로 확인

개념 정리

  • 동기 제너레이터는 값을 만들 때까지 그 자리에서 블로킹 — 다른 작업이 끼어들 수 없음
  • 비동기 제너레이터(async def + async for + await)는 대기하는 동안 다른 코루틴이 실행될 수 있음
  • FastAPI 서버에서 동기 방식으로 스트리밍을 처리하면, 한 요청을 처리하는 동안 다른 사용자 요청을 못 받을 수 있음
  • 실제 서비스에서는 AsyncOpenAI + async for로 여러 사용자를 동시에 서빙

핵심 코드

ESSENTIAL async def async_gen(): for i in range(3): await asyncio.sleep(1) yield i async def do_other_work(): for i in range(3): await asyncio.sleep(0.3) print("다른 작업 처리 중...", i) await asyncio.gather(consume(), do_other_work()) # 출력: 다른 작업 3회가 먼저 끝나고, 받은 값 0/1/2가 1초 간격으로 이어짐

FAQ

실제로 출력 순서가 왜 그렇게 나와?

async_gen은 1초마다 값을 하나씩 내놓는데, 그 대기 시간 동안 do_other_work가 0.3초 간격으로 끼어들어 먼저 3번 다 실행되어버린다(0.9초 만에 완료). 이후 1초, 2초, 3초 시점에 받은 값이 순서대로 출력된다.

CONCEPT

배포와 CI/CD

SDLC, CI/CD, 배포 전략 3가지

개념 정리

  • 배포: 개발된 소프트웨어를 운영 환경에 올리는 과정. 빌드 -> 패키징 -> 배포 -> 실행 단계로 구성
  • SDLC(소프트웨어 개발 생명주기): 개발(기능 구현/테스트 코드) -> 테스트(통합 테스트/QA) -> 운영(품질/안정성 확보)
  • CI(지속적 통합): 변경 코드를 주기적으로 중앙 리포지토리에 병합하고 자동 빌드/유닛 테스트 실행. 통합 오류 조기 발견이 목표
  • CD(지속적 전달, Delivery): CI 통과 빌드를 테스트 환경에 자동 배포하고 배포 준비 상태를 검증. 운영 배포는 사람이 수동 승인
  • CD(지속적 배포, Deployment): 모든 자동화 단계를 통과하면 수동 개입 없이 운영 환경까지 자동 배포. 높은 수준의 테스트 자동화/모니터링/롤백 전략 필수
  • 롤링 배포: 여러 서버 중 일부씩 새 버전으로 교체
  • 블루-그린 배포: 트래픽을 한 번에 구버전에서 신버전으로 전환
  • 카나리 배포: 신버전으로 트래픽을 점진적으로 옮김

FAQ

지속적 전달(Delivery)과 지속적 배포(Deployment)는 뭐가 달라?

둘 다 CI를 통과한 빌드를 자동으로 배포 준비까지 진행하지만, Delivery는 운영 환경 배포 시점에 사람의 수동 승인이 필요하고, Deployment는 그 승인 과정까지 없이 완전 자동으로 운영 환경에 배포된다.

TOOLING

git 설정 & VS Code-GitHub 연동

git config의 전역/로컬 구조, VS Code 연동 이점

개념 정리

  • git config --global은 컴퓨터 전체에 적용되는 기본값, --global 없이 프로젝트 폴더 안에서 설정하면 그 프로젝트에만 적용되는 로컬 설정
  • 개인 프로젝트와 학교/회사 프로젝트에서 서로 다른 이메일/이름을 쓰고 싶을 때 로컬 설정을 활용
  • git config --list로 현재 적용된 설정 확인 가능, --global --list / --local --list로 범위별 확인 가능
  • VS Code에 GitHub을 연동하면 소스 제어 탭에서 커밋/푸시, 변경사항 diff 확인, 커밋 히스토리 추적, PR 관리까지 GUI로 처리 가능

핵심 코드

ESSENTIAL git config --global user.name "이하진" git config --global user.email "본인의진짜이메일@example.com" git config --global --list # 전역 설정만 보기 git config --local --list # 지금 폴더의 로컬 설정만 보기

FAQ

user.email이 이상하게 설정돼 있으면 뭐가 문제야?

커밋 작성자 정보로 기록되기 때문에, GitHub 계정에 등록된 이메일과 다르면 커밋이 내 프로필과 연결되지 않을 수 있다. GitHub 계정 이메일(또는 GitHub 제공 noreply 이메일)로 맞춰주는 게 좋다.
